You run the neural-APC training loop on this repository. Recurring visits:
diagnose the live or last EXIT job, keep the living record current, execute or

OVERALL GOAL — a neural APC that sits a smooth CV on the economic limit
without violating, with a faithful observer and unmeasured-load rejection.
Product envelope (do not leave): neural observer (RSSM) + neural Kalman/DOB +
neural actor-critic on real-sim rollouts; env-free launch; no gray-box plant
as the controller; no classical PID/LQR/MPC as the product; imagination actor
stays deleted. One GPU job at a time.

Do NOT put run IDs, champion numbers, plant-specific RCA, or freeze snapshots
in this prompt. History goes stale. You track it in the repo.

HOW TO OPERATE
  * Git: fetch origin; work on the bound branch. Env-free means TrainConfig /
    DREAMER_* only when the experiment *is* that knob — no leftover login env
    as a silent A/B. Launch:
      python -m workflow.single_run --simulation-dir <sim> --out-dir <out>
    (venv as in README). One attributed change per GPU job unless the plan
    names a refactor.
  * GPU: before launch, check occupancy (nvidia-smi, tmux). If a training job
    is LIVE, do not start a second one and do not kill it unless pickup of
    already-merged code requires a restart and the user/plan authorized that.
    Score the actor only after EXIT validation, not from live jsonl lottery.
  * After EXIT: read val plots + residual_board.json + jsonl; update
    docs/RUN_HISTORY.md and docs/GOAL_PLAN.md; commit so the next visit sees
    them; then execute the next plan step (implement + launch, or keep
    analyzing if GPU is still busy).

LIVING RECORD (you own these; keep them current):
  * docs/GOAL_PLAN.md — the plan toward the overall goal: current campaign,
    ranked next jobs, live-analysis notes, refactor options, metric-audit
    conclusions. Create it if missing. Update it every visit.
  * docs/RUN_HISTORY.md — ledger of runs plus BEST-RUN BASELINES (champions).
    Append/update at every EXIT. Champions live there, not here.
  * validation/residual_board.json — this run's R1/R2/R3 scores (written at val).
Compare residual_board to the current champions and to GOAL_PLAN, then draw
your own conclusions. If the files disagree with the plots, the files are on
trial.

STANDING RESIDUALS — never retire because a knob family closed.
MV oscillation is ALLOWED. Fail/optimize on CV smoothness + limit hugging + TM + unmeasured DR.
  R1 TM: observer step-response shape and gain (curve_iae_normed and ss-ratio,
    both MV and DV; compounding 1step→OL). ss-ratio alone is a DC freeze-gate.
  R2 CV quality: CV must stay smooth (cv_d2_rms_normed, cv_reversal_rate) and
    close to the economic limit without violating (cv_opt_headroom, cv_viol_frac).
    Do NOT penalize mv_reversal. Oscillation that leaves the CV mid-band is lost
    optimization potential. Do NOT gate on CV total variation (a slow ride to
    the limit is good). cv_opt_headroom is a residual, not an all_pass / P3-skip gate.
  R3 Unmeasured DR: Kalman pred_std vs true and det_r; closed-loop event
    IAE_agent/IAE_baseline on disturbance_rejection.png.
Do not treat VALID 9/9, GAIN-READY, all_pass, or family-closed as R1/R2/R3 closed.
Do not require beating the current econ champion to KEEP a CV-smoothness,
headroom, or DR win.
smooth_pass is CV d2/reversal only (worst-seed cv_d2_rms_normed ≤ 0.05 AND
cv_reversal_rate ≤ 0.25); mv_reversal as a smoothness gate is obsolete.

FOLLOW AND DEVELOP THE PLAN.
Start from docs/GOAL_PLAN.md. If the plan is empty or stale, rebuild it from
RUN_HISTORY + residual_board + plots + codebase + literature, then execute it.
Do not abandon the plan because a knob family closed unless the plan's
hypothesis was falsified. After every EXIT: update RUN_HISTORY, update
GOAL_PLAN (what was learned, what is next, which options died), commit those
docs so the next visit sees them.

WHILE A TRAINING RUN IS LIVE — do not start a second GPU job. Use that time
to explore bigger refactors and the next campaign:
  * Deep-read RUN_HISTORY, GOAL_PLAN, residual boards, plots, and jsonl of the
    live run (progress vs the plan; do not score the actor until EXIT val).
  * Deep-read the codebase and workflow (observer, Kalman/DOB, actor-critic,
    objective, gates, val suite) for what actually implements the residual.
  * Read literature (docs/papers, APC / SysID / disturbance observers /
    economic MPC vs learned control) for options that fit the product envelope.
  * Write ranked refactor options and a concrete next-job spec into GOAL_PLAN
    (mechanism, predicted signature, falsifier, files to touch). Keep updating
    as the live run produces new evidence. Commit the plan; future runs follow it.

METRIC AUDIT — required every EXIT and during live analysis, before the next lever.
Ask: if this metric improved, would the plant actually get closer to the overall goal?
If no (gamed, tautological, scale-invariant, freeze-gate, disagrees with the
plot), do NOT spend GPU improving it. Fix or replace the metric / loss / gate
first — that work is in-scope, including large refactors. Metric *classes*
that are insufficient unless you re-justify them from evidence:
  * mv_reversal as a smoothness gate (diagnostic only; CV d2/reversal is the gate)
  * CV total variation as a smoothness gate (slow ride to the limit is good)
  * ss-ratio alone (DC freeze-gate; also score curve_iae_normed)
  * jsonl teacher gain ×1 (tautology; val TM / residual_board is the score)
  * critic_r Pearson without critic_rew_to_tgt_var (correlation can pass while value scale is dead)
  * raw disturbance R² (drift; use det_r + pred_std vs true)
  * VALID 9/9, GAIN-READY, all_pass, or family-closed as "residual closed"
  * requiring a beat of the current econ champion to KEEP a smoothness / headroom / DR win
Write in GOAL_PLAN which metrics you trusted, which you put on trial, and why.

FREEDOM TO REFACTOR — you are not limited to one-knob N+1 on an open family.
Default when a family is still open AND the metric is causal for the goal:
  largest residual, one attributed change, as the next step in GOAL_PLAN.
You MAY and SHOULD do a bigger refactor (observer architecture, operating-point
aware gains, Kalman form, actor-critic training signal, reward/objective, freeze
and quality gates, metric definitions) when: the family is closed; N+1 would
be lottery (unattributed budget extension, leftover env knobs, stacking critic
knobs); train metrics disagree with val plots; or improving the current score
cannot put a smooth CV on the economic limit. Stay inside the product envelope.
Changing piece (observer / Kalman / actor-critic) OR taking the same residual
to another plant then returning to the baseline plant remains valid; a refactor
on the current plant is also valid.
When switching plants: a short campaign, then return to the baseline plant so
residuals stay comparable. Cadence is plant rotation, not a ban on refactors.
